# اكتمال الخطط والدفع ووضوح التشخيص الذكي

**التاريخ:** 2026-07-26
**الحالة:** معتمد للتنفيذ بعد مراجعة المستخدم للنص المكتوب
**النطاق:** الويب، واجهات API، تطبيق Flutter، ولوحة الإدارة

## 1. الهدف

تحويل وظائف الخطط والدفع والتشخيص الذكي من قدرات جزئية أو مخفية إلى رحلة مكتملة ومرئية تعمل بالقواعد نفسها في الويب والتطبيق. يشمل الإصدار تغيير المستخدم لخطته، تعيين الإدارة للخطط فرديًا وجماعيًا، تشغيل عدة بوابات دفع فعلية، وإعادة بناء نماذج التشخيص لتلائم طبيعة كل إجابة بدل حصرها في اختيار واحد.

يصدر العمل كتسليم موحد؛ لا تُنشر واجهات بلا خدمات خلفية عاملة، ولا تُعلن بوابة دفع قبل اكتمال الإنشاء والتحقق والإشعارات والاسترداد.

## 2. مبادئ حماية البيانات والمال

- تبقى الاشتراكات والخطط والمدفوعات الحالية دون تعديل تلقائي.
- كل تغيير إداري مالي أو جماعي يحتاج معاينة ثم تأكيدًا صريحًا ويسجل المنفذ والوقت والقيم السابقة والجديدة.
- لا تمنح إعادة اختيار الخطة نفسها رصيدًا جديدًا، ولا يؤدي تكرار رد البوابة أو الإشعار إلى منح مزدوج.
- لا تُفعّل خطة مدفوعة إلا بعد تحقق الخادم من حالة الدفع والمبلغ والعملة والمرجع.
- تخزن مفاتيح البوابات مشفرة، ولا تعاد قيم الأسرار إلى الويب أو التطبيق بعد الحفظ.
- لا يلمس الخادم بيانات البطاقة الخام. تستخدم صفحات الدفع المستضافة أو رموز الدفع وفق تكامل كل مزود.

## 3. معمارية الخطط والاشتراكات

### 3.1 دورة حياة الاشتراك

يمثل الاشتراك حالة فعلية لها: الخطة الحالية، الحالة، بداية الفترة، نهاية الفترة، التجديد، الإلغاء المجدول، مصدر التغيير، وآخر دفعة مرتبطة. الحالات المدعومة هي: نشط، بانتظار الدفع، إلغاء مجدول، منتهٍ، وموقوف إداريًا.

- الخطة المجانية تُفعّل دون دفع، لكن لا تمنح رصيد البداية إلا عند إنشاء الاشتراك أول مرة أو بقرار إداري صريح.
- الترقية المدفوعة تدخل حالة انتظار حتى نجاح الدفع ثم تصبح فعالة فورًا.
- التخفيض أو الرجوع إلى المجانية يمكن تنفيذه فورًا أو عند نهاية الفترة، ويعرض أثره قبل التأكيد.
- شراء الخطة نفسها خلال الفترة لا ينشئ منحة مكررة؛ يعالج كتجديد واضح أو يُرفض إن كان تجديدها غير مستحق.
- انتهاء الفترة دون تجديد يحول الاشتراك وفق سياسة الخطة إلى المجانية، من دون حذف مشاريع أو تقارير المستخدم.

### 3.2 إدارة المستخدم الفردي

تعرض شاشة المستخدم للإدارة كل مساحات العمل وخطتها وحالتها وفترتها ورصيدها. يستطيع الآدمن:

- تعيين خطة عامة أو خاصة.
- اختيار النفاذ الفوري أو نهاية الفترة أو تاريخ محدد.
- تحديد معالجة الرصيد صراحة: إبقاؤه، إضافة فرق، إضافة قيمة محددة، أو ضبطه على قيمة محددة.
- إيقاف الاشتراك أو استئنافه أو جدولة إلغائه.
- معاينة الأثر ثم تأكيد العملية.

### 3.3 التغيير الجماعي والخطط الخاصة

تسمح الإدارة باختيار المستخدمين يدويًا أو تصفيتهم حسب الخطة والحالة وتاريخ التسجيل. تظهر معاينة بعدد المتأثرين وأسمائهم وأثر الرصيد قبل التنفيذ. تُنفذ العملية بمعاملة آمنة لكل مساحة، ويُعرض تقرير نجاح وفشل تفصيلي قابل للتنزيل.

يمكن إنشاء خطة خاصة غير ظاهرة للعامة، أو استنساخ خطة عامة وتعديل السعر والحدود والميزات، ثم إسنادها لمستخدم واحد أو مجموعة. لا تُنشأ استثناءات خفية داخل الكود؛ كل تخصيص يصبح خطة مسماة قابلة للتدقيق.

## 4. منظومة الدفع متعددة البوابات

### 4.1 البوابات

يدعم الإصدار:

- Moyasar: الدفع بالريال عبر صفحة/مكوّن مستضاف مع تحقق خلفي وإشعارات.
- Tap: الدفع بالبطاقات ووسائل الدفع المتاحة للحساب عبر مسار التحويل والتحقق.
- PayPal: Orders API v2 بالإنشاء والموافقة والالتقاط والإشعارات.
- التحويل البنكي/اليدوي: تعليمات مخصصة، مرجع تحويل، رفع إثبات اختياري، واعتماد أو رفض من الإدارة.

كل مزود ينفذ عقدًا موحدًا: اختبار الاتصال، إنشاء جلسة الدفع، التحقق، معالجة الإشعار، الاسترداد، وتفسير الحالة. تبقى تفاصيل المزود داخل محوله ولا تتسرب إلى منطق الخطط.

### 4.2 إدارة البوابات

تعرض شاشة واحدة كتالوج البوابات وإضافة البوابة مع مفاتيحها في العملية نفسها. لكل بوابة:

- اسم ظاهر وترتيب وطريقة عرض.
- وضع اختبار أو مباشر.
- العملات ومعامل التحويل عند الحاجة.
- الحقول السرية الخاصة بالمزود.
- رابط العودة والإلغاء والإشعار القابل للنسخ.
- زر اختبار اتصال يعرض نتيجة مفهومة ووقت آخر اختبار.
- تفعيل مستقل؛ يمكن تشغيل عدة بوابات مع تحديد الافتراضية.

لا تُفعّل بوابة إلكترونية في الوضع المباشر قبل اكتمال الحقول الإلزامية ونجاح اختبار الاتصال. تغيير البوابة الافتراضية لا يعطل البوابات الأخرى ولا يمنع إكمال دفعة بدأت سابقًا.

### 4.3 رحلة الدفع

يعرض الويب والتطبيق البوابات الفعالة للمستخدم قبل إنشاء الدفع. يرسل الخادم معرف البوابة المختارة، ويعيد رابط دفع خارجيًا أو حالة تحويل يدوي. بعد العودة يجلب الخادم العملية من المزود ويطابق الحالة والمبلغ والعملة قبل الوفاء.

تدعم المدفوعات الحالات: بدأت، بانتظار المستخدم، بانتظار اعتماد، مدفوعة، فاشلة، ملغاة، مستردة جزئيًا، ومستردة. يسجل النظام معرفًا فريدًا للطلب والإشعار كي تكون كل العمليات متكررة بأمان.

تعرض صفحة المستخدم سجل المدفوعات، تفاصيل الخطة أو الحزمة، البوابة، المبلغ الأساسي والمحصّل، الحالة، التاريخ، وإيصالًا قابلًا للطباعة. تعرض الإدارة البحث والتصفية والتصدير والاعتماد اليدوي والاسترداد مع تأكيد مالي.

## 5. وضوح التشخيص الذكي

لا يبقى التشخيص زرًا داخل صفحة المشروع فقط. يظهر في:

- بطاقة رئيسية في لوحة المستخدم بعنوان واضح وشرح قصير وزر «ابدأ التشخيص الذكي».
- عنصر مستقل دائم في قائمة التنقل.
- كل بطاقة مشروع مع حالة آخر جلسة: لم يبدأ، قيد الإجابة، قيد التحليل، مكتمل، أو يحتاج تدخلًا.
- صفحة المشروع كالإجراء الرئيسي.
- شاشة ما بعد إنشاء أول مشروع، مع انتقال مباشر إلى اختيار عمق التشخيص.
- الصفحة العامة والتسعير كقيمة أساسية للمنتج، دون عرض نتائج خاصة قبل تسجيل الدخول.
- الصفحة الرئيسية للتطبيق، وبطاقات المشاريع، والتنقل السفلي أو قائمة الإجراءات الأساسية.
- لوحة الإدارة مع أعداد الجلسات وحالاتها، إضافة إلى إدارة كتالوج الأسئلة.

إذا لم يكن للمستخدم مشروع، يفتح زر التشخيص إنشاء المشروع ثم يعيده تلقائيًا إلى بدء التشخيص. إذا توجد جلسة غير مكتملة، يصبح الإجراء «أكمل التشخيص» بدل إنشاء جلسة جديدة بالصدفة.

## 6. تدقيق جميع النماذج وأنواع الإجابات

### 6.1 القاعدة الحاكمة

يُستخدم الاختيار الأحادي فقط عندما تكون البدائل متعارضة منطقيًا أو عندما يلزم تحديد أولوية واحدة صريحة. أي سؤال يمكن أن تنطبق عليه عدة حالات يتحول إلى اختيار متعدد، ترتيب، أو مجموعة حقول مترابطة. لا يغير النظام نوع السؤال المنشور بصمت؛ ينشئ إصدارًا جديدًا ويحتفظ بإجابات الجلسات القديمة قابلة للقراءة.

### 6.2 الأنواع المدعومة في الويب وFlutter والإدارة

- اختيار واحد وبطاقات مواقف متعارضة.
- اختيار متعدد مع حد أدنى وأقصى وخيار «أخرى» بنص تابع.
- ترتيب عناصر بالسحب أو بأزرار صعود وهبوط قابلة للوصول.
- نطاق رقمي بحد أدنى وأقصى ووحدة.
- رقم مباشر مع العملة أو النسبة أو الزمن.
- مقياس اتفاق أو تكرار.
- نص قصير ونص طويل.
- رابط وبريد وتاريخ.
- نعم/لا/غير متأكد.
- مجموعة متكررة، مثل عدة شرائح عملاء أو منافسين مع تفاصيل كل عنصر.
- رفع ملف أو صورة مع الموافقة الصريحة.
- تأكيد معلومة استنتجها النظام مع إمكانية تصحيحها.
- «لا أعرف» و«تخطي» وفق قواعد السؤال، ويظلان مختلفين دلاليًا.

### 6.3 عملية التدقيق

يُراجع كتالوج الاستشارة وجميع حقول الأدوات والنماذج العامة ونماذج المشروع والفوترة والإدارة. يُنتج مدقق آلي قائمة بكل سؤال اختياري ونوعه وعدد خياراته وسبب استخدام النوع. يفشل تدقيق الإصدار عندما:

- يكون سؤال يحتمل تعدد الحالات من نوع أحادي دون تبرير مسجل.
- يرسل الويب أو Flutter قيمة لا يقبلها تحقق الخادم.
- لا يستطيع المستخدم تعديل إجابة متعددة في شاشة المراجعة.
- تضيع وحدة الرقم أو ترتيب العناصر أو قيمة «أخرى» في التقرير.
- تختلف رحلة الويب عن التطبيق في نوع الإجابة أو قواعدها.

### 6.4 تجربة الاستخدام

لا تعرض الشاشة سؤالًا طويلًا كقائمة راديو كثيفة. تستخدم بطاقات قابلة للمس، وتوضح «يمكنك اختيار أكثر من إجابة» وعدد الاختيارات عند الحاجة. يحتفظ النموذج بإجابته أثناء الخطأ، ويعرض رسالة محددة قرب الحقل. شاشة المراجعة تعيد نفس عنصر الإدخال الأصلي بكل الاختيارات والقيم المحفوظة.

## 7. واجهات الإدارة والتطبيق

تضاف لوحة فوترة واضحة في الإدارة تضم: الخطط، الميزات، التعيينات، العمليات الجماعية، البوابات، المدفوعات، والاستردادات. تعرض الصفحة الرئيسية للإدارة تنبيهات البوابات غير المجهزة والمدفوعات المعلقة والاشتراكات المنتهية.

يستهلك Flutter العقود نفسها ولا يكرر قواعد الاستحقاق أو الدفع. يتضمن تطبيق الإدارة إدارة الخطط وتعيينها واختيار المستخدمين وتشغيل البوابات بعد اختبارها ومراجعة المدفوعات. لا تظهر الأسرار في التطبيق بعد الحفظ.

## 8. الأخطاء والاسترداد التشغيلي

- فشل إنشاء الدفع لا ينشئ اشتراكًا ولا يمنح رصيدًا، ويترك سببًا آمنًا للمستخدم وتفصيلًا تقنيًا في السجل.
- انقطاع العودة لا يفقد الدفع؛ يكمله الإشعار أو تحقق الحالة عند فتح سجل الدفع.
- فشل عنصر داخل تغيير جماعي لا يخفي بقية النتائج، ويمكن إعادة محاولة العناصر الفاشلة فقط.
- حذف خطة مستخدمة ممنوع؛ يمكن إخفاؤها أو أرشفتها.
- حذف بوابة لها مدفوعات ممنوع؛ يمكن تعطيلها مع بقاء القدرة على التحقق من العمليات السابقة.
- كل إجراء مالي يستخدم قفل قاعدة بيانات ومعرف تكرار ومعاملة تمنع المنح المزدوج.

## 9. الاختبارات ومعيار القبول

يبدأ التنفيذ باختبارات فاشلة ثم يضاف أقل كود يحققها. يشمل القبول:

- اختبارات تغيير الخطة والترقية والتخفيض والتجديد ومنع تكرار الرصيد.
- اختبارات تعيين مستخدم واحد ومجموعة والمعاينة والتأكيد وسجل التدقيق.
- اختبارات كل مزود للدفع: إنشاء، عودة، إشعار صحيح وخاطئ، مبلغ أو عملة غير مطابقين، تكرار، فشل، إلغاء، واسترداد.
- اختبار تفعيل عدة بوابات واختيار المستخدم للبوابة وعدم تبديل العملية إلى بوابة أخرى أثناء الإكمال.
- اختبارات ظهور التشخيص في كل نقاط الدخول واستئناف الجلسة غير المكتملة.
- اختبار كل نوع إجابة في Blade وAPI وFlutter، والحفظ والتعديل والمراجعة والتقرير.
- تدقيق آلي لكل كتالوج الأسئلة لاكتشاف الاختيار الأحادي غير المبرر.
- اختبارات الصلاحيات والملكية وCSRF وتشفير الأسرار وعدم تسربها.
- تشغيل مجموعة Laravel كاملة، تدقيق التنسيق، بناء الويب، تحليل Flutter واختباراته، ثم بناء APK وAAB موقّعين.

لا تُعد النسخة مكتملة إذا كانت أي بوابة معلنة بلا تحقق فعلي، أو كانت وظيفة إدارية بلا واجهة، أو ظهر نوع سؤال في الويب دون نظيره في التطبيق، أو ظل التشخيص معتمدًا على اكتشافه عرضًا داخل المشروع.
