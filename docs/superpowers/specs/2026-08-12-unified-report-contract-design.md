# تصميم عقد التقارير التشخيصية الموحّد

**التاريخ:** 2026-08-12  
**الحالة:** معتمد للتنفيذ  
**القرار البصري:** العقد الجديد داخل هوية المنصة الحالية (`STYLESEED.md`)

## 1. الهدف

منع نشر أي مخرج تشخيصي في khaledsaad.net إذا كان يحمل توصية ناقصة، أو قالبًا
لا يطابق هدفها، أو درجة غير قابلة لإعادة الحساب، أو ادعاءً بلا دليل أو افتراض
معلن. ينطبق العقد على التوليد الآلي والموقّع والمختلط، وعلى الويب وPDF وAPI
وتطبيق Flutter والتقارير التجميعية وبطاقات الجاهزية والمشاركة العامة.

الموقع ما زال في مرحلة التجربة. لذلك تُعامل التقارير السابقة كلها كبيانات
تجريبية، ويُنفّذ انتقال نظيف لنطاق التقارير بعد نسخة احتياطية، مع إبقاء
الحسابات ومساحات العمل والمشاريع والإجابات والأدلة والإدارة والفوترة ومفتاح
`APP_KEY` دون تغيير.

## 2. حدود النطاق

### داخل النطاق

- تقارير الأدوات الإحدى عشرة في `database/data/tools`.
- المسارات `automated` و`signed` و`hybrid`.
- تقرير صاحب المشروع، موجز الوكالة، والملف التشغيلي المشتق منهما.
- بطاقة جاهزية الظهور للذكاء الاصطناعي وقوائم الإصلاح.
- نتائج الحضور وGEO حين تعرض حكمًا أو توصية.
- الويب وPDF وJSON وAPI v1 وFlutter والروابط المشتركة والنموذج العام.
- سجل التحقق والمراجعات والآثار البشرية وفجوات مكتبة القوالب.
- أمر انتقال مقيّد ينظف مخرجات التقارير التجريبية فقط.

### خارج النطاق

- تغيير أسئلة الأدوات أو منطق الاشتراكات والفوترة.
- حذف حسابات أو مشاريع أو إجابات أو أدلة أو استشارات.
- إنشاء منتج أو قاعدة بيانات أو رحلة موازية.
- النشر الفعلي إلى الإنتاج؛ نهاية هذا العمل هي حزمة جاهزة للنشر.

## 3. مصدر الحقيقة

تبقى الكيانات الحالية `reports`, `findings`, `recommendations`, و`agency_reports`
مصدر الحقيقة. لا يُنشأ مخزن JSON بديل لها. يضاف `contract_payload` إلى التقرير
كلقطة إصدار غير قابلة للتعديل بعد النشر، ويُشتق منها العرض في كل الأسطح.

جدول `objectives` هو قاموس الأهداف المركزي. كل توصية تحمل `objective_id`، وكل
قالب يحمل الهدف نفسه. `TemplateResolver` لا يقبل النوع المرئي (`message`,
`post`, `spreadsheet`) كمدخل اختيار؛ النوع نتيجة للقالب المختار بالهدف.

## 4. أنواع المخرجات

### 4.1 التقرير التشخيصي

يحمل غلافًا موحّدًا، درجة قابلة للتدقيق، نتائج، افتراضات، وتوصيات. كل توصية
تلتزم بالحقول:

- `deliverable`
- `template`
- `done_when`
- `first_five_minutes`
- `expected_failure`

وتحمل أيضًا `impact`, `effort`, `duration_days`, و`metric.objective_id`.

### 4.2 التقرير التجميعي

لا يعيد اختراع توصيات. يقرأ التوصيات المنشورة المصدّقة من التقارير المصدرية
وينقل عقدها كاملًا إلى الأولويات. أي مصدر غير صالح يمنع إصدار التجميع، ولا
يُعوّض بوصف عام.

### 4.3 بطاقات الجاهزية والنتائج المتخصصة

الفقرة المعلوماتية لا تُجبر على عقد التوصية. لكن أي عنصر يأمر المستخدم بفعل
شيء يصير `action_item` ويُحوّل إلى توصية كاملة مرتبطة بهدف. جميع النتائج، حتى
غير الإجرائية، تلتزم بالدليل والإسناد وصحة الدرجة.

## 5. الإسناد والمراجعات

القيم الرسمية:

- `automated`: تحليل آلي بقواعد ثابتة.
- `signed`: تحليل كتبه خالد، ويلزم أثر بشري واحد على الأقل.
- `hybrid`: مسودة آلية عُدلت يدويًا، مع حفظ فرق التعديل.

يستمر `review_mode` مؤقتًا للتوافق مع API v1، لكن `provenance` هو الحقل الرسمي.
عند استيراد نتيجة يدوية لتشغيل لم يسبق نشر تقريره تكون `signed`. عند تعديل
تقرير آلي منشور تكون `hybrid`، وتُكتب مراجعة `report_revisions` وفروقها.

الآثار البشرية هي `note`, `reorder`, و`override`. لا يُنشر `signed` أو `hybrid`
بلا أثر. تختفي كل عبارات نفي الآلة، وتظهر تسمية محايدة وسطر مسؤولية مناسب.

## 6. نموذج البيانات

تضاف بهجرة أمامية واحدة مترابطة:

- `objectives`
- `recommendation_templates`
- `template_bindings`
- `report_revisions`
- `validation_findings`
- `human_traces`
- `template_gaps`
- `scoring_items`

وتضاف حقول العقد إلى الجداول الحالية:

- `reports`: `provenance`, `score_raw`, `score_max`, `issued_at`, `authored_at`,
  `authored_by`, `validation_status`, `schema_version`, `contract_payload`.
- `findings`: `evidence_answer_id`, `evidence_quote`.
- `recommendations`: `objective_id`, `metric_objective_id`, `deliverable`,
  `done_when`, `first_five_minutes`, `expected_failure`, `duration_days`,
  `template_id`, `degraded`, `degrade_reason`, `fallback_coaching`.
- `agency_reports`: `provenance`, `validation_status`, `schema_version`.

تستخدم مفاتيح أجنبية قابلة للحذف الآمن حيث يلزم، وفهارس الأهداف والتقارير
والحالة. القيم المالية والمشفرة لا تدخل أي هجرة أو أمر تنظيف.

## 7. خط التوليد

```text
Answers
  -> DeterministicScorer
  -> FindingsBuilder
  -> RecommendationContractBuilder
  -> TemplateResolver::forObjective
  -> SemanticValidator
  -> repair once (automated only)
  -> degrade invalid recommendation
  -> ReportAssembler
  -> JSON Schema assertion
  -> atomic persist as published snapshot
  -> shared renderer (web / PDF / API / Flutter)
```

الحساب الحتمي يرجع `raw`, `max`, و`score`. عناصر التفصيل تُحفظ في
`scoring_items`. لا يملك النموذج حق كتابة الدرجة.

في المسار اليدوي تُطبق البوابة نفسها دون إصلاح آلي. المخالفة تعود للمراجع
بمسارات دقيقة. في المسار المختلط يُسجل الفرق والسبب والفاعل قبل النشر.

## 8. التحقق الدلالي

`SemanticValidator` لا يعدّل الحمولة. يرجع `ValidationReport` يحوي مخالفات
`code`, `severity`, `path`, `message`, و`suggested_action` للقواعد R01–R15.

التشابه يحسب Jaccard بعد `ArabicText::normalize` وإزالة علامات الترقيم والكلمات
الوظيفية. القوائم العامة الأربع ممنوعة كتسلسل كامل. الإحالة إلى طلب لاحق
ممنوعة. الدرجات تقارن بمجموع البنود بسماح ±0.5.

بعد محاولة الإصلاح الواحدة، التوصية المخالفة تُحفظ داخليًا كـ`degraded` ولا
تظهر كتوصية قابلة للتنفيذ. إذا كان سببها غياب قالب، يعرض السطح حالة صريحة
«لا يوجد قالب مطابق لهذه التوصية بعد»، ويسجل `template_gaps`. لا يملأ النظام
قالبًا من هدف آخر ولا ينسخ الخطوات إلى القالب.

وجود مخالفة `block` غير قابلة للعزل، مثل الدرجة الخاطئة أو غياب أثر موقّع،
يمنع نشر التقرير كله. تحفظ جميع النتائج، الناجحة والمرفوضة، للتدقيق.

## 9. مكتبة الأهداف والقوالب

تُعرّف الأهداف في ملف بيانات واحد وتُزرع في قاعدة البيانات. تعلن كل أداة قائمة
الأهداف المسموح بها، مع هدف افتراضي حتمي لكل قاعدة تقييم. المولّد لا يرسل هدفًا
خارج هذه القائمة.

كل قالب يحمل `required_context`. الربط يستخدم `template_bindings` إلى مفاتيح
إجابات أو ملف المشروع، بتحويلات مغلقة ومعلومة. غياب سياق إلزامي يجعل القالب
غير قابل للحل بدل اختراع قيمة.

## 10. العرض

`STYLESEED.md` هو المصدر البصري الوحيد. نأخذ من البرومبت البنية الورقية، غياب
الظلال عن بطاقات التقرير، الحقول الصريحة، منطق RTL، أرقام tabular، والطباعة
A4، لكن لا نستبدل لون المنصة أو أنصاف أقطارها بهوية ثانية.

المكوّنات المشتركة:

- `provenance-badge`
- `score-equation`
- `recommendation-contract`
- `recommendation-template`
- `human-trace-margin`
- `validation-state`

تستخدم Blade وPDF وFlutter نفس DTO. يخفي PDF أزرار النسخ، وتمنع البطاقات من
الانقسام حيث يمكن. الرابط المشترك لا يعيد صياغة المحتوى بل يطبّق سياسة إظهار.

## 11. الانتقال التجريبي

الأمر `reports:trial-reset` يعمل بوضع معاينة افتراضيًا. التنفيذ يتطلب:

1. `--execute`
2. `--backup=<مسار موجود وقابل للكتابة>`
3. تأكيد أن البيئة ليست production، أو `--production-confirmation` صريحًا.
4. تصدير counts وJSON للمعرّفات واللقطات قبل الحذف.

ينظف فقط ملفات PDF وروابط المشاركة و`agency_reports` و`reports` وما يتبعها
و`tool_runs` المكتملة المرتبطة بالتقارير عند اختيار ذلك صراحة. لا يلمس
المشاريع أو الإجابات المشتركة أو الاستشارات أو الفوترة أو المستخدمين.

## 12. التوافق

- API v1 يحتفظ بالحقول القديمة ويضيف الجديدة.
- Flutter يقبل الحقول الجديدة ويعرض نقصها بوضوح أثناء فترة الانتقال.
- التقارير ذات `schema_version < 2` لا يمكن مشاركتها أو إعادة توليد PDF لها.
- نموذج التقرير العام يُبنى من fixture مصدّق لا من HTML مستقل.

## 13. بوابة القبول

- كل R01–R15 له اختبار وحدة مباشر.
- اختبار التقرير الحقيقي ذي الدرجة 58 وست نتائج يفشل قبل الإصلاح بسبب
  R01/R02/R03/R04، ويمر بعد إصلاح fixture.
- الآلي واليدوي والمختلط يمرون من البوابة نفسها.
- التقرير التجميعي يرفض مصدرًا غير مصدّق.
- الويب وPDF وAPI وFlutter تعرض عقدًا واحدًا متطابقًا.
- لا توجد عبارة تنفي الآلة في المصدر أو الاختبارات.
- اختبارات A4 تفحص عدم غياب `break-inside: avoid` وإخفاء أدوات الشاشة.
- أمر التنظيف يجتاز dry-run واختبار الحدود ولا يحذف بيانات خارج النطاق.
