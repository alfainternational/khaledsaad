# تصميم الإصدار الكامل للويب والتطبيق

## 1. القرار المعتمد

يُنجز المشروع بوصفه إصدارًا متكاملًا واحدًا، لا مجموعة تحسينات منفصلة تُعلن مكتملة قبل أوانها. يجوز تقسيم التنفيذ داخليًا إلى مسارات ومراحل لتقليل المخاطر، لكن لا يُعد الهدف منجزًا ولا يُنشر الإصدار النهائي حتى تجتاز المنصة بوابة قبول واحدة تشمل الويب والتطبيق واللغة والتقارير والبناء والنشر.

يبقى Laravel مصدر الحقيقة للبيانات والصلاحيات والحسابات والتقارير والدفع. يستهلك الويب وFlutter الخدمات نفسها من خلال طبقة تطبيق موحدة وواجهات API موثقة، ولا يُعاد تنفيذ منطق الأعمال داخل Flutter.

المقصود بالمطابقة بنسبة 100% هو المطابقة الوظيفية والمعلوماتية:

- كل قدرة متاحة لدور معين في الويب لها نظير واضح في التطبيق، ما لم تكن قدرة خاصة بالمتصفح أو متجر التطبيقات، وعندها يُوثق البديل المكافئ.
- تعرض النسختان البيانات والدرجات والحالات والصلاحيات والرسائل نفسها من المصدر نفسه.
- يمكن أن يختلف ترتيب العناصر وفق طبيعة الشاشة، لكن لا تُحذف وظيفة أو معلومة بسبب اختلاف الجهاز.
- لا تُثبت المطابقة بالانطباع؛ بل بمصفوفة قابلة للفحص واختبارات تعاقد ورحلات مستخدم.

## 2. الحالة المرجعية

أظهر التدقيق السابق للتنفيذ ما يأتي:

- يعمل الموقع المنشور من `https://khaledsaad.net/` دون ظهور `/public` في العنوان.
- لا توجد حاليًا صفحة تنزيل أو حزمة تطبيق منشورة في الموقع.
- ينجح بناء Vite، وينجح `flutter analyze --no-pub`، وتنجح اختبارات Flutter الحالية.
- نجحت اختبارات Laravel الحالية عند تشغيلها في دفعات، بإجمالي 231 اختبارًا و981 تحققًا.
- يفشل `pint --test` في ملف مساعد واحد تحت `deploy/`.
- يحتوي Flutter الحالي على وظائف أساسية للمستخدم، لكنه لا يغطي التجربة العامة ولوحة الإدارة وجميع قدرات النمو الموجودة في الويب.
- إعدادا Firebase الصحيحان موجودان خارج المستودع، لكنهما غير مدمجين في التطبيق الحالي.
- معرفا Android وiOS الحاليان لا يطابقان معرفات Firebase المعتمدة، وإصدار Android يستخدم توقيعًا تجريبيًا ورابط API محليًا.
- توجد عبارات متفرقة مرتبطة بلهجات محلية وتفاوت في تسمية بعض المفاهيم.

هذه النقاط خط أساس، وليست تعريفًا للنطاق النهائي.

## 3. مبادئ التنفيذ

### 3.1 مصدر حقيقة واحد

- تُنفذ قواعد الأعمال في خدمات Laravel القابلة للاستخدام من الويب وAPI والمهام الخلفية.
- لا يحسب Flutter الدرجات أو الميزانيات أو حالات الاستحقاق أو صلاحيات المزايا.
- تتلقى Blade وFlutter نماذج عرض متقاربة البنية من مقدّمي عرض مركزيين.
- أي تغيير في عقد API يتطلب اختبار تعاقد يثبت بقاء الويب والتطبيق متوافقين.

### 3.2 الحفاظ على البيانات

- لا تُحذف بيانات الإنتاج ولا تُعاد تهيئة قاعدة البيانات.
- تكون الترحيلات إضافية أو قابلة للعكس، مع نسخ احتياطي قبل النشر.
- تبقى التقارير القديمة مرتبطة بإصدار الأداة والبرومبت الذي أنشأها.
- يُنشأ إصدار جديد للبرومبتات بدل تعديل الإصدار المقفول.

### 3.3 إصدار نهائي واحد

تُدمج المسارات تدريجيًا في بيئة العمل، لكن النشر النهائي لا يبدأ قبل اكتمال:

1. مصفوفة المطابقة.
2. مراجعة اللغة.
3. تجاوب الويب.
4. وظائف Flutter.
5. Firebase والتوقيع.
6. جودة التقارير.
7. اختبارات القبول والبناء.

## 4. مصفوفة المطابقة

يُنشأ ملف آلي القراءة في `docs/product/parity-matrix.yaml`. يمثل كل سجل قدرة واحدة، ويحتوي على:

- المعرف الثابت للقدرة.
- دور المستخدم: زائر، عميل، مدير.
- مسار الويب وإجراءه.
- مسار API المكافئ.
- شاشة Flutter وإجراءها.
- حالات التحميل والفراغ والخطأ والنجاح ومنع الصلاحية.
- اختبار الويب، واختبار API، واختبار Flutter.
- حالة التنفيذ والتحقق.
- ملاحظة البديل المكافئ إن كانت القدرة مرتبطة بالمنصة.

لا تُحسب القدرة مكتملة إذا كان أي حقل إثبات مفقودًا. ويجب أن تصل المصفوفة إلى 100% دون سجلات مستثناة غير مبررة.

- فتح روابط التقارير المشتركة الآمنة.
- صفحة تنزيل التطبيق ومعلومات الإصدار.

### 4.2 قدرات العميل

- لوحة الحساب والإشعارات.
- إنشاء المشاريع وتعديلها وعرضها.
- الأدوات الإحدى عشرة بكل أنواع الحقول والأسئلة الشرطية.
- الحفظ والاستئناف والرفع والحذف والفحص المسبق.
- التحليل الفوري والهجين، والانتظار، وإعادة المحاولة، والمراجعة اليدوية.

### 4.3 قدرات المدير

- لوحة الإدارة ومؤشرات الاستخدام.
- إدارة الأدوات والإصدارات والبرومبتات وحالات النشر.
- إدارة المزايا والخطط وباقات الرصيد.
- إدارة بوابات الدفع وتفعيلها وتعطيلها.
- إدارة المستخدمين والأدوار والأرصدة.
- مراجعة المدفوعات اليدوية وقبولها أو رفضها.
- التقارير اليدوية والتصدير والحفظ.
- إعدادات المنصة.

تظهر واجهة الإدارة في Flutter فقط للحساب المصرح له، وتستخدم API محميًا بسياسات الخادم. لا يكفي إخفاء الأزرار على الجهاز لمنع الوصول.

## 5. بنية API والتطبيق

### 5.1 API

يبقى الإصدار الحالي تحت `/api/v1`. تُستكمل المسارات الناقصة دون كسر العقود الحالية، وتشمل:

- محتوى التجربة العامة وتجربة الضيف.
- استعادة كلمة المرور.
- نبض النمو وGEO ومختبر الجمهور بجميع العمليات الموجودة في الويب.
- جميع عمليات التقرير الموحد.
- تفاصيل الدفع وحالات الإلغاء والعودة.
- واجهات الإدارة المقابلة للمسارات الإدارية.
- تسجيل جهاز الإشعارات وتحديث رمزه وحذفه.
- بيان إصدار التطبيق والتنزيل.

تلتزم الاستجابات بغلاف موحد للبيانات والأخطاء ورسائل التحقق. وتكون أخطاء الملكية 404 عندما يلزم عدم كشف المورد، وأخطاء الصلاحية 403، وأخطاء التحقق 422.

### 5.2 Flutter

يُنظم التطبيق إلى أربعة أغلفة:

1. غلاف الزائر: الرئيسية، الأدوات، التجربة، الصفحات القانونية، والتنزيل/معلومات الإصدار.
2. غلاف المصادقة: التسجيل والدخول واستعادة كلمة المرور.
3. غلاف العميل: المشاريع والأدوات والتقارير والنمو والحساب والفوترة.
4. غلاف المدير: الإدارة الكاملة للحسابات المصرح لها.

تستخدم الشاشات مستودعات حسب المجال بدل مستودع ضخم واحد، مع عميل HTTP مشترك وإدارة جلسة مركزية. تُستخدم نماذج منفصلة لعقود الشبكة ونماذج العرض عندما يمنع ذلك تسرب تفاصيل API إلى الواجهة.

يجب أن تدعم كل شاشة:

- التحميل الأولي والتحديث.
- حالة عدم وجود بيانات.
- خطأ الشبكة وإعادة المحاولة.
- انتهاء الجلسة.
- منع الميزة حسب الخطة.
- إمكانية الوصول واتجاه RTL وتكبير النص.
- الروابط العميقة للوجهة الصحيحة.

## 7. جودة التقارير والبرومبتات

تُرقّى منظومة البرومبتات إلى إصدار جديد بدل تعديل النسخة التاريخية. يتكون المسار من:

1. حقائق موثقة ومدخلات موثوقة.
2. حسابات حتمية ينفذها الخادم.
3. مسودة تحليل.
4. تحقق دلالي من الادعاءات والأرقام والتعارضات.
5. إصلاح آلي للناتج المخالف.
6. تركيب نهائي خاص بكل أداة.

كل ادعاء يحمل نوعًا: حقيقة، حساب، معيار إرشادي، أو فرضية. وكل رقم يحمل القيمة والوحدة والمصدر والصيغة والافتراضات. ولا تعرض التوصية رقمًا أو هدفًا غير منسوب إلى مدخل أو حساب أو معيار معلن.

يكون لكل أداة مخطط إخراج يناسبها بدل مخطط عام وحيد. ويُحد الناتج التنفيذي إلى ثلاث أولويات رئيسية، لكل منها خطوة أولى ومسؤول وموعد ومؤشر وخط أساس وهدف ومصدر.

يُبنى سجل تقييم لا يقل عن ثماني حالات لكل أداة، أي 88 حالة للأدوات الإحدى عشرة، ويقارن الإصدار القديم والجديد في وضع الظل قبل اعتماد الإصدار الجديد.

تُعامل إجابات المستخدم ومرفقاته بوصفها بيانات غير موثوقة، ويُمنع تنفيذ أي تعليمات مكتوبة داخلها.

## 8. اللغة والأسلوب

### 8.1 الصوت المعتمد

اللغة عربية واضحة ومحايدة وقريبة من القارئ، من دون مفردات مرتبطة ببلد أو لهجة بعينها. المخاطبة مباشرة ومحترمة بصيغة المفرد، وتبتعد عن الفصحى المتكلفة وعن العامية المحلية.

أمثلة التحويل:

- «الصفحة دي ما موجودة» ← «هذه الصفحة غير موجودة».
- «وين وصل مشروعك؟» ← «إلى أي مرحلة وصل مشروعك؟».
- «خلّيه حيًا» ← «فعّل المتابعة المستمرة».
- «مش توقّع» ← «وليس توقعًا».
- «عندي حساب» ← «لدي حساب».
- «ناقص عليك» ← «البيانات الناقصة».

- البرومبتات والنصوص الافتراضية.

## 9. تجاوب الويب وإمكانية الوصول

تُختبر جميع صفحات الزائر والعميل والمدير عند العروض:

- 320، 360، 375، 390، 412 بكسل للهواتف.
- 768 و1024 بكسل للأجهزة اللوحية.
- 1280 و1440 بكسل لسطح المكتب.

تشمل معايير القبول:

- عدم وجود تمرير أفقي غير مقصود.
- عدم قص النص أو الأزرار أو الحقول أو الجداول.
- تحويل الجداول إلى بطاقات عند إمكان الحفاظ على العلاقة بين الحقول، أو وضعها داخل تمرير أفقي محلي معلن لا يسبب تمرير الصفحة كلها.
- مناطق لمس لا تقل عن 44×44 بكسل.
- بقاء التنقل والعمليات الأساسية متاحة بلوحة المفاتيح.
- تسميات واضحة للحقول والأيقونات.
- تحقيق WCAG AA: نسبة 4.5:1 للنص العادي و3:1 للنص الكبير والعناصر الرسومية، مع حالة تركيز مرئية.
- دعم `prefers-reduced-motion`.
- نجاح الصفحة عند تكبير النص إلى 200%.
- عدم الاعتماد على التحويم وحده.

تُستخدم اختبارات متصفح آلية ولقطات مرجعية، مع مراجعة بصرية للصفحات ذات المخاطر العالية، خصوصًا المعالجات والتقارير والإدارة والفوترة.

## 10. البناء والتوزيع

### 10.1 Android

- يضبط `applicationId` على المعرف المعتمد من Firebase.
- يُنشأ مفتاح توقيع إنتاجي لا يدخل المستودع.
- تُقرأ بيانات التوقيع من متغيرات أو ملف محلي مستثنى.
- يُبنى APK عام للتنزيل المباشر.
- يُبنى AAB بوصفه حزمة متجر.
- يُختبر تثبيت APK وتشغيله على جهاز أو محاكي جديد.

### 10.2 iOS

- يضبط Bundle ID على المعرف المعتمد.
- تكتمل إعدادات Firebase والقدرات والإشعارات والروابط.
- يُختبر التحليل والوحدات المشتركة على Windows، ثم يُنفذ البناء والتوقيع النهائيان على macOS.
- يحتاج النشر الفعلي إلى حساب Apple Developer وشهادة وملف Provisioning ومعرف App Store. لا يُدعى اكتمال نشر iOS قبل توفرها ونجاح الأرشفة.

### 10.3 صفحة التنزيل

تُنشأ صفحة `/download` تعرض:

- رقم الإصدار وتاريخ النشر.
- متطلبات النظام والحجم.
- زر تنزيل APK.
- بصمة SHA-256 للتحقق.
- سجل التغييرات.
- رابط App Store عند توفره.
- تعليمات تثبيت مختصرة وآمنة.

يُنشأ بيان إصدار آلي القراءة، ولا يُستبدل ملف إصدار قديم بصمت؛ تحفظ الإصدارات بأسماء تحتوي رقم الإصدار، ويشير رابط `latest` إلى النسخة المعتمدة.

## 11. الأمن والخصوصية

- لا تدخل مفاتيح خاصة أو كلمات مرور أو مفاتيح توقيع أو أسرار مزودي الدفع في Git أو حزمة Flutter.
- يُدوّر مفتاح SSH الذي كُشف سابقًا قبل النشر النهائي.
- تُخزن رموز الأجهزة والإشعارات بشكل آمن ويمكن إلغاؤها عند تسجيل الخروج.
- تخضع كل واجهات العميل والمدير لسياسات ملكية وصلاحية على الخادم.
- تُراجع رفع الملفات والتنزيلات والروابط المشتركة ومحددات المعدل.
- تُراجع سجلات الأخطاء لمنع تسريب المدخلات الحساسة.
- تُرفق الملفات المنشورة ببصمات تحقق، وتُقدم عبر HTTPS فقط.

## 12. التعامل مع الأخطاء

- لا يؤدي فشل الذكاء الاصطناعي إلى فقد الإجابات أو الرصيد.
- لا يؤدي فشل Firebase إلى منع الاستخدام الأساسي للتطبيق.
- تعرض الشبكة البطيئة حالة واضحة ولا تكرر عملية مالية تلقائيًا.
- تستخدم عمليات الدفع والتوليد مفاتيح عدم تكرار حيث يلزم.
- تحفظ المعالجات تقدم المستخدم بعد كل خطوة ناجحة.
- تعرض أخطاء الإنتاج رسالة محايدة مع معرف تتبع، دون تفاصيل تقنية.
- تستعيد عمليات النشر النسخة السابقة عند فشل الهجرة أو فحص الصحة.

## 13. الاختبارات وبوابة القبول

### 13.1 اختبارات الخادم والويب

- Laravel Pint.

### 13.2 اختبارات Flutter

- جميع اختبارات الوحدات والواجهات.
- اختبارات عقود النماذج مقابل استجابات API.
- اختبارات رحلة الزائر والعميل والمدير.

- مقارنة رسائل العمليات المشتركة بين الويب والتطبيق.

### 13.4 تعريف 100%

لا تُعد المنصة مكتملة إلا إذا:

- بلغت مصفوفة القدرات 100%.
- كانت جميع اختبارات الويب وAPI وFlutter مرتبطة بسجلات المصفوفة وناجحة.
- اجتازت جميع المقاسات المستهدفة دون خلل حرج أو عالٍ.
- اجتاز فاحص اللغة والمراجعة البشرية.
- نجح تثبيت APK المنشور وتشغيله على API الإنتاج.
- نجح تنزيله من صفحة الموقع وكانت بصمته مطابقة.
- كانت Firebase عاملة في نسختي Android وiOS من المصدر، وAndroid متحققًا منه على جهاز.
- نجح فحص الإنتاج للمسارات العامة والعميل والمدير والتنزيل.
- كانت خطة الرجوع والنسخة الاحتياطية مجربتين.
- لم يبق أي عنصر مطلوب بحالة غير متحقق أو دليل غير مباشر.

## 14. النشر

يُنفذ النشر بالترتيب:

1. إنشاء نسخة احتياطية من قاعدة البيانات والملفات الحالية.
2. بناء الأصول وحزم التطبيق من نسخة Git محددة.
3. تشغيل جميع بوابات القبول محليًا.
4. رفع إصدار في مجلد نسخة جديد دون حذف النسخة السابقة.
5. تشغيل الترحيلات الآمنة.
6. تحديث الرابط الفعلي للإصدار.
7. تنظيف كاش Laravel، وإعادة تشغيل عمال الصف إذا تغيّر كود المهام أو إعداد الصف أو كانت هناك مهام طويلة تعمل بالإصدار السابق.
8. نشر APK وبيان الإصدار وصفحة التنزيل.
9. تنفيذ فحوص الدخان العامة والمصادق عليها والإدارية.
10. التحقق من التنزيل والبصمة والتثبيت.
11. مراقبة الأخطاء والأداء بعد النشر.

إذا فشل فحص حرج، يُعاد الرابط إلى الإصدار السابق وتُستعاد قاعدة البيانات فقط إذا كانت الهجرة غير متوافقة مع الرجوع وقد ثبتت الحاجة إلى ذلك.

## 15. ترتيب مسارات التنفيذ

هذه مواصفة رئيسية جامعة، وحجمها أكبر من خطة تنفيذ واحدة يمكن مراجعتها بأمان. لذلك تُحوّل بعد اعتمادها إلى خطة رئيسية وعدة خطط تنفيذ فرعية مرتبة، ولكل خطة نطاق واضح واختبارات ودليل اكتمال. لا يغيّر هذا التقسيم بوابة الإصدار الواحدة ولا يسمح بإعلان الهدف مكتملًا قبل اجتياز جميع الخطط.

ترتيب التنفيذ الداخلي هو:

1. سجل المطابقة وقاموس اللغة وأدوات الفحص.
2. استقرار Laravel وعقود API.
3. مراجعة لغة الويب وتجربة الهاتف.
4. بنية Flutter العامة والمصادقة.
5. وظائف العميل الكاملة.
6. وظائف الإدارة.
7. Firebase والروابط والإشعارات.
8. برومبتات وتقارير الإصدار الجديد.
9. التوقيع وصفحة التنزيل.
10. اختبار شامل، نشر، وتدقيق اكتمال الإنتاج.

هذا الترتيب لا يحول أي خطوة إلى تسليم جزئي؛ إنه وسيلة لضمان أن الإصدار النهائي المتكامل قابل للاختبار والرجوع.

## 16. القيود الخارجية

- بناء وتوقيع iOS النهائيان يحتاجان macOS وحساب Apple Developer صالحًا.
- نشر App Store يحتاج App Store ID وموافقة Apple.
- توقيع Android الإنتاجي يحتاج كلمة مرور آمنة لمفتاح التوقيع.
- اختبار الإشعارات الحقيقية يحتاج جهازًا فعليًا أو بيئة Firebase صالحة.

تُستكمل جميع الأعمال التي لا تعتمد على هذه المدخلات، لكن لا تُقدّم ادعاءات اكتمال تخص اعتمادًا خارجيًا لم يتحقق فعليًا.
